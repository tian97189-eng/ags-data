## build-apk.bat PowerShell 调 java 的 -D 参数被吞（v5 修复，提交待定）

用户重跑 build-apk.bat 报错 `[6/7] Building APK`：

```
错误: 找不到或无法加载主类 .gradle.appname=gradlew
原因: java.lang.ClassNotFoundException: /gradle/appname=gradlew
```

**根因**：第 82 行用 PowerShell 的 `&` 调用 java.exe，但 PowerShell 会把以 `-` 开头的参数（如 `-Dorg.gradle.appname=gradlew`）当成自己的 cmdlet 参数尝试绑定；解析失败时把 `-D` 前缀吃掉，java 收到的是 `.gradle.appname=gradlew`（没有 `-D`），于是把它当成了"主类名"→ ClassNotFoundException。

**修复**：在 `& 'java.exe'` 后加 `--%`（PowerShell stop-parsing token），告诉 PowerShell「从这开始所有参数原样传给外部程序，不要再做参数绑定」；同时把 classpath 路径的双引号改对（`--%` 后单引号不会被解析为引号，双引号才会被 Win32 CommandLineToArgvW 当成 token 引号）。另外去掉了原来的 `2>&1`（`--%` 模式下 PowerShell 重定向语法不再被识别，会被当成 java 参数；gradle 已用 `--console=plain`，主要错误也走 stdout）。

**验证**：等用户重跑 build-apk.bat 确认成功。

## v7：弃用 cmd 内嵌 PS 命令串，改为 .ps1 脚本（12:30）

用户重跑 v6 后报错：
```
'换行符?token' 不是内部或外部命令
'hell' 不是内部或外部命令
```

- 注意：`.ps1` 文件里 `--%` 后所有 token 必须字面量（PS 在 stop-parsing 模式下不展开变量、不解析引号），路径全部写死。
- **教训（写进 MEMORY.md）**：Windows PowerShell 5.1 在 cmd `-Command "..."` 字符串里使用 `--%` 行为不可靠；要把 PS 命令写到独立 `.ps1` 文件再 `powershell -File` 执行。

## v10：真根因——gradle daemon 停止异常导致 errorlevel 非 0（13:18）

用户明确说"从没手动关过窗口"，推翻 v9 的"用户关窗"假设。查 13:14 那次 gradle daemon 日志：
```
BUILD SUCCESSFUL in 31s
...
java.lang.IllegalStateException: Cannot start managing file contention because this handler has been closed.
```
**真根因**：gradle 8.14.3 即使 BUILD SUCCESSFUL，停止 single-use daemon 时抛 IllegalStateException，
使 java 退出码非 0 → bat 里 `if errorlevel 1 goto fail` 误判失败 → 跳 :fail → **`[7/7] copy APK
to Desktop` 被永远跳过** → 桌面一直没 APK。跟用户关不关窗无关。

**v10 修复**：[6/7] java 命令后**删掉 `if errorlevel 1 goto fail`**，改为直接进 [7/7] 用
`if exist "%APK%"` 判断（APK 生成就 copy+SUCCESS，没生成才 fail）。这样 daemon 停止异常
不影响判断。同时已把 12:49 的 APK 重新复制到桌面供用户即时使用。

**教训（长期）**：gradle 用 `--no-daemon` 仍会 fork single-use daemon，其停止时在 Windows 上
可能抛 IllegalStateException 使进程退出码非 0；**判断 gradle 成败不能用退出码，要看输出里
有没有 "BUILD SUCCESSFUL" 或产物文件是否生成**。
## v11：真·最终根因——[7/7] if 块内 echo 含括号导致 cmd 语法错误（13:48）

用户反复"跑完了没 APK"。加诊断日志后定位：日志停在 `[DIAG] USERPROFILE` 之后，
`if exist "%APK%" (` 既没走 true 也没走 false → [7/7] if 块从没执行。

排查过程（走了弯路）：
- 先怀疑 LF 换行符 → 实际文件是干净 CRLF（sed 管道把 \r 吃掉误导了）
- 用最小复现测试 + 模拟测试（java 换 echo）逐步定位
- **真根因**：`[7/7] if 块内 echo 文本含 `(do NOT uninstall first)` 和 `(release)` 括号。
  cmd 解析 if 代码块时会把 echo 里的 `)` 当成块结束符，括号错乱报 `此时不应有 .`，
  导致整个 if 块语法错误、一行都不执行。**这是 cmd 批处理的经典陷阱**。
- 顺带修了另一个隐患：bat 里中文注释（UTF-8 编码）在 cmd GBK 代码页下字节错位，
  会破坏 rem 注释和后续行解析 → 全部改成英文（遵守项目"bat 全英文"约定）。

**v11 修复**：① 去掉 if 块内 echo 的括号（`(do NOT...)` → `- do NOT...`，`(release)` → `release`）；
② 中文注释全部改英文。模拟测试（java 换 echo）验证 [7/7] 完整走通 SUCCESS + copy。

**最终结论**：之前 v10 归因的"daemon 异常退出码"不是根因（诊断日志显示 errorlevel=0）。
真正根因是 if 块内 echo 括号。教训：**cmd 批处理 if 块内的 echo 文本绝不能含 `(` `)`，
否则报"此时不应有 ."整个块失败**。
