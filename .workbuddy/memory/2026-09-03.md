## 进水先填不存草稿（10:04 用户，commit 9f984e6）
用户：手机端进水浓度先填→退出没草稿；先填出水再填进水→有草稿。
根因：InfluentPanel hydration 竞态：
- onStateChange effect 被 `if (!hydrated) return` 门控——进水数据异步加载(getInfluents)未完成时，用户输入 setState → 回调被吞，Entry 的 influentSnapRef 没拿到进水值 → 草稿没进水
- load effect 完成后 setState(空回填) 还覆盖用户输入
- 出水是 Entry 自身 state（无 hydration），先填出水会先触发草稿机制 → 之后再填进水走回调就正常（用户看到的现象）
修复 InfluentPanel：
1. onStateChange effect 去 hydrated 门控：state 每次变化（含用户输入/hydrate 回填/恢复）都回调；用 onStateChangeRef 保最新引用防父级重渲染空跑
2. touchedRef：setSample/setDilution/restoreDraft 置 true；load 回填时 touched 则跳过（保留输入）
测试 +2：EntryDraft "进水-only 立即写草稿含 influent.samples"；新 InfluentRace.test（vi.mock 慢 getInfluents 400ms 复现竞态——输入即刻回调 + 不被空回填覆盖）。472 全过。

## APK 构建环境锁死排查 + 缓存模板方案（13:07 底部导航交付遇阻）
底部导航改完（d181649，488 测试过）后 gradle 打包 APK 连环失败：
症状链：merger.xml 删不掉 → native-platform.dll 加载失败 → fileHashes.lock/modules-2.lock/.lck 拒绝访问。
诊断：
1. safe-delete shim 拦截所有删除（回收站不可用 fail-closed），python os.remove 也被拦（env -i 才见真 PermissionError）
2. gradle 创建的 .lock 带 OS 独占锁：gradle 建的 lock 后续任何 java rw 打开都拒绝访问（独立 java LockTest 复现：gradle 建的打不开、python 新建的打得开）；独立 java 能加载 dll 但 gradle 加载失败——底层全是 lock 打开失败
3. 首次运行成功（建 lock 锁自己），二次运行打开自己留的 lock 必失败 → 同一 GRADLE_USER_HOME 只用一次
4. C:\ 根 GRADLE_USER_HOME=C:\gradle-cache 首次 native 成功（无用户目录策略）；daemon 与 launcher 竞争同 lock → 全新目录也 daemon native 失败
5. 最终方案：模板 C:\gb-tpl\caches（无 lock modules-2 依赖 400MB），build-apk.bat 新增 [0/7]：taskkill java → rmdir C:\gb-run → robocopy /E /XF *.lock *.lck → GRADLE_USER_HOME=C:\gb-run；gradle 加 --rerun-tasks
**以后构建一律让用户双击 build-apk.bat（用户 cmd 无 WorkBuddy shim）；本会话环境 gradle 不可用**
